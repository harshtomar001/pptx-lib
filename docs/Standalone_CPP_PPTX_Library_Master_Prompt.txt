MASTER PROMPT — BUILD A STANDALONE C++ POWERPOINT/PPTX DOCUMENT LIBRARY

ROLE

You are a senior C++ systems engineer, document-format engineer, graphics/rendering engineer, and library architect.

Your task is to design and implement a standalone, reusable, production-quality C++ library for reading, interpreting, laying out, and rendering Microsoft PowerPoint presentations.

THIS IS A LIBRARY PROJECT ONLY.

STRICT SCOPE

The project MUST NOT contain:
- Android code
- Java/Kotlin code
- JNI
- Android NDK integration
- Android UI
- XML Android layouts
- PDF Studio code
- Activities/Fragments/ViewModels
- mobile-specific APIs
- platform-specific UI code
- application-specific business logic

The result must be a normal, portable C++ library that another application can consume later.

The library should expose a clean public C++ API and be buildable independently with CMake.

PRIMARY GOAL

Build a reusable C++ presentation engine capable of:

1. Opening .pptx files.
2. Parsing the OOXML package.
3. Understanding presentation structure.
4. Resolving relationships.
5. Resolving themes, masters, and layouts.
6. Parsing slides.
7. Parsing common PowerPoint shapes and objects.
8. Performing layout and coordinate transformations.
9. Rendering slides to a generic raster target.
10. Rendering individual objects.
11. Rendering thumbnails.
12. Handling large presentations efficiently.
13. Using bounded memory.
14. Supporting concurrent/background rendering safely.
15. Providing deterministic rendering where practical.
16. Failing gracefully on unsupported or malformed content.

LEGACY .PPT

Treat legacy binary .ppt support as a separate capability.

Do NOT let legacy .ppt support compromise the architecture for modern .pptx.

First build a strong .pptx engine.

If legacy .ppt support requires a separate parser/backend, design the library so that it can be added later.

IMPORTANT LIBRARY PHILOSOPHY

Do not build a monolithic "PPTX to image" function.

Build a proper document engine with layers:

Input/package layer
        ↓
OOXML/XML layer
        ↓
Relationship/resource layer
        ↓
Presentation model
        ↓
Style/theme inheritance
        ↓
Layout engine
        ↓
Rendering abstraction
        ↓
Raster/vector backend

Each layer must have clear responsibilities.

PUBLIC API

Design a stable, minimal public API.

The public API should conceptually allow:

Presentation presentation = Presentation::open(path);

size_t count = presentation.slideCount();

const Slide& slide = presentation.slide(index);

RenderOptions options;
options.width = 1920;
options.height = 1080;

RenderTarget target(...);

renderer.render(slide, target, options);

Do not expose internal XML structures through the public API.

Do not force users of the library to understand OOXML.

The API should eventually support both:

- File-based loading
- Stream-based loading where practical

Use exceptions or a documented Result/Error model consistently. Do not mix error-handling philosophies arbitrarily.

PPTX PACKAGE ARCHITECTURE

Understand and implement the OOXML package correctly.

A PPTX is a ZIP-based package containing parts and relationships.

Typical structure:

[pptx]
 ├── [Content_Types].xml
 ├── _rels/
 ├── ppt/
 │   ├── presentation.xml
 │   ├── slides/
 │   ├── slideLayouts/
 │   ├── slideMasters/
 │   ├── theme/
 │   ├── media/
 │   ├── charts/
 │   ├── embeddings/
 │   └── _rels/
 └── docProps/

The engine must resolve relationships rather than relying on filenames or assumed numbering.

PACKAGE SAFETY

PPTX files are untrusted input.

The package layer must protect against:
- ZIP path traversal
- malformed ZIP entries
- decompression bombs
- huge declared sizes
- excessive nesting where applicable
- invalid relationships
- unexpected external references
- malformed XML
- resource exhaustion

Do not blindly extract the entire ZIP package to disk.

Prefer controlled, random-access package reading where practical.

Put configurable safety limits on:
- maximum uncompressed package size
- maximum XML size
- maximum image size
- maximum number of parts
- maximum slide count
- maximum relationship count
- maximum rendering dimensions

The library must fail predictably when limits are exceeded.

XML PARSING

Use a mature, permissively licensed XML parser rather than writing a complete XML parser from scratch unless there is a compelling engineering reason.

Requirements:
- namespace-aware parsing
- safe parsing
- no external entity/network loading
- efficient traversal
- minimal unnecessary DOM duplication

Keep XML parser details out of the public API.

RELATIONSHIPS

Implement proper OOXML relationship resolution.

Support:
- slide → layout
- layout → master
- master → theme
- slide → media
- slide → charts
- other relevant relationships

Never assume relationship IDs map directly to filenames.

PRESENTATION MODEL

Create an internal normalized object model.

Core objects:

Presentation
 ├── Slide
 │    ├── Shape
 │    ├── Group
 │    ├── Text
 │    ├── Image
 │    ├── Table
 │    └── Chart
 ├── SlideLayout
 ├── SlideMaster
 └── Theme

Keep the model independent from XML node names.

The renderer should operate on the normalized model rather than parsing XML while drawing.

SHAPE MODEL

Support common shapes first:

- rectangle
- rounded rectangle
- ellipse
- line
- arc where practical
- freeform/path
- polygon
- connectors
- groups

Each shape should support, where applicable:
- position
- size
- rotation
- flip
- fill
- stroke
- opacity/transparency
- line width
- dash style
- transform
- clipping
- z-order

Use a proper transform system.

COORDINATE SYSTEM

PowerPoint uses its own coordinate units and transformations.

Implement correct conversion to renderer coordinates.

Do not scatter conversion constants throughout the code.

Centralize:
- EMU conversion
- angle conversion
- scale conversion
- transform matrices
- slide coordinate mapping

Use a matrix/transform abstraction.

TEXT ENGINE

Text rendering is one of the most important parts of the project.

Support initially:
- text boxes
- paragraphs
- text runs
- font size
- font family
- bold
- italic
- underline
- strike-through where practical
- foreground color
- alignment
- vertical alignment
- margins
- wrapping
- bullets
- numbering
- line spacing
- paragraph spacing
- indentation

Text must be laid out before rendering.

Do NOT simply draw each string at an approximate coordinate.

Separate:

Text content
    ↓
Text layout
    ↓
Glyph/run positions
    ↓
Text rendering

FONT HANDLING

Design a FontManager abstraction.

Support:
- font lookup
- fallback fonts
- missing-font handling
- font metrics
- font loading
- caching

Do not assume a particular operating system's font directory.

The core library should allow the host application to provide fonts.

If a system-specific font backend is required, isolate it behind an interface.

IMAGES

Support common embedded image formats used by PPTX.

At minimum investigate:
- PNG
- JPEG
- other common OOXML-compatible raster formats

The image subsystem should:
- decode lazily
- cache decoded resources
- avoid duplicate decoding
- respect maximum dimensions
- support scaling
- support cropping
- support transparency
- support rotation/transforms

Do not decode every image in the presentation during file opening.

TABLES

Implement a real table model.

Support:
- rows
- columns
- cell text
- cell fills
- borders
- alignment
- row/column sizes
- merged cells where practical

CHARTS

Charts should have a separate subsystem.

Initially support common chart types where feasible.

Do not allow chart implementation to contaminate basic shape/text rendering.

If some chart feature cannot be rendered:
- render the supported portion where possible
- report unsupported features through diagnostics
- never crash

THEMES

Implement theme inheritance properly.

Support:
- theme colors
- font schemes
- color transformations
- default styles where applicable

Resolve theme values before rendering.

SLIDE MASTER / LAYOUT

Implement:

Presentation
  ↓
Slide Master
  ↓
Slide Layout
  ↓
Slide
  ↓
Object

Correct inheritance and override behavior is important.

Do not treat each slide as a completely isolated document.

Z-ORDER

Preserve the correct drawing order.

The renderer should process objects in their effective z-order.

GROUPS

Groups must support:
- nested shapes
- group transforms
- scaling
- rotation
- inherited transforms
- clipping where applicable

Use a transform stack rather than manually modifying every coordinate.

RENDERING ARCHITECTURE

Do NOT tightly couple the renderer to a specific UI toolkit.

Create an abstract rendering layer.

Conceptually:

Renderer
   ↓
RenderTarget
   ↓
Canvas / Graphics backend

The core API should allow a backend to render into:
- raster bitmap
- memory buffer
- host-provided graphics backend

The first production backend may be raster-based.

Avoid introducing Android-specific Canvas types.

RASTER RENDERING

Support rendering at arbitrary requested dimensions.

For example:

RenderOptions:
- width
- height
- scale
- background behavior
- antialiasing
- quality

Never render a 4K slide if the caller only requested a 800px thumbnail.

Render at target resolution.

THUMBNAILS

Provide efficient thumbnail rendering.

Thumbnail rendering should:
- use lower resolution
- avoid unnecessary high-resolution image decoding
- share parsed resources where possible
- use a separate bounded cache

MEMORY OPTIMIZATION

This is a core requirement.

Never:
- render all slides eagerly
- retain every bitmap
- duplicate large image buffers
- copy large XML strings unnecessarily
- keep entire decompressed package contents in memory without reason
- create unbounded caches

Use:
- lazy parsing
- lazy resource decoding
- LRU caches
- resource deduplication
- streaming where practical
- move semantics
- RAII
- bounded allocations
- buffer reuse where safe

A 200-slide presentation should not require 200 full-resolution slide bitmaps in memory.

RESOURCE CACHING

Use separate caches where appropriate:

- package/part metadata
- parsed themes
- fonts
- decoded images
- slide models
- rendered thumbnails
- rendered slides

Cache keys must include enough information to prevent incorrect reuse.

Caches must have explicit size limits.

THREADING

The library should be thread-safe at the appropriate level.

Do not assume the entire Presentation object is freely mutable from multiple threads.

Prefer immutable presentation data after parsing where practical.

Support concurrent rendering of independent slides if safe.

Avoid global mutable state.

Do not create unbounded worker threads.

Make the threading model clearly documented.

CANCELLATION

Long-running operations should support cancellation.

For example:

CancellationToken token;

renderer.render(slide, target, options, token);

Rendering/parsing should periodically check cancellation.

This is important for applications that abandon a render request.
